

## 🚀 Инструкция по запуску

1. Поднимите инфраструктуру и окружение:

   tripgoctl cluster start
   tripgoctl environment start
   tripgoctl connect


2. Примените миграции базы данных:

   make migrate

3. Запустите сервис:

   make run

### ⚙️ Переменные окружения (.env)
Сервис конфигурируется через переменные окружения (примеры значений смотрите в .env.example):

HTTP_ADDR — адрес и порт для запуска HTTP-сервера (например, :8080).

DATABASE_URL — строка подключения к PostgreSQL.

SHUTDOWN_TIMEOUT — таймаут для graceful shutdown (например, 10s).

LOG_LEVEL — уровень логирования.

Параметры пула соединений: DATABASE_MAX_CONNS, DATABASE_MIN_CONNS, DATABASE_CONNECT_TIMEOUT, DATABASE_QUERY_TIMEOUT, DATABASE_MAX_CONN_LIFETIME


## 🛠️ Принятые решения

### 1. Уровень изоляции транзакций
* **Выбранный уровень:** `ReadCommitted` (по умолчанию в PostgreSQL).
* **Почему:** Данный уровень изоляции достаточен для предотвращения «грязного чтения» (dirty reads). Совместно с уникальным индексом в базе данных и проверками на уровне бизнес-логики он обеспечивает корректную защиту от гонок (race conditions) при одновременном создании поездок или попытке занять водителя, не создавая избыточных блокировок производительности.

### 2. Реализация менеджера транзакций
* Менеджер транзакций (`TxManager`) скрывает работу с `pgx` от бизнес-логики и репозиториев.
* Открытая транзакция сохраняется в контексте (`context.Context`) под специальным ключом. 
* Репозитории через вспомогательную функцию проверяют наличие транзакции в контексте: если она есть, запрос выполняется в её рамках, если нет — через общий пул соединений (`pgxpool`).
* Поддерживаются вложенные вызовы (переиспользование существующей транзакции) и гарантированный `Rollback` в случае возникновения ошибки или паники (`panic`).

### 3. Запрет двух активных поездок на одного водителя
* Защита реализована на двух уровнях:
  1. **На уровне БД:** Уникальный частичный индекс (или ограничение уникальности с учетом статуса), который не позволяет вставить более одной активной поездки для одного `driver_id`. При нарушении этого правила база возвращает ошибку с кодом `23505`, которая на уровне репозитория перехватывается и преобразуется в бизнес-ошибку (статус `409` / код `driver_busy`).
  2. **На уровне завершения (`FinishTrip`):** Обновление статуса поездки в БД выполнено атомарно с проверкой текущего состояния (`WHERE id = ? AND status = 'active'`). Проверка количества затронутых строк (`RowsAffected`) защищает от параллельных запросов на завершение.
